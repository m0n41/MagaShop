# Техническое задание: REST API для интернет-магазина

## 1. Цель проекта

Добавить к существующему интернет-магазину на Django REST API на базе Django REST Framework. API должен предоставлять данные и операции для внешнего клиента, например мобильного приложения или отдельного frontend.

API работает с теми же моделями и базой данных, что и HTML-сайт. Переписывать сайт на DRF и дублировать модели не нужно.

## 2. Текущее состояние

- Проект использует Django и PostgreSQL.
- Приложения разделены по предметным областям: `catalog`, `cart`, `orders`, `users`, `reviews`, `wishlist`, `coupon` и другие.
- DRF и `rest_framework.authtoken` уже установлены.
- В настройках DRF включены `TokenAuthentication`, глобальный `AllowAny` и пагинация `LimitOffsetPagination` с размером страницы 10.
- API URL-карта каталога подключена под `/api/v1/` через `catalog/urls_api.py`.
- Сериализатор товара уже преобразует теги в список названий.
- Существующие HTML views, URL и сценарии сайта необходимо сохранить.
- Первая версия API не включает регистрацию, вход или JWT. Сначала нужно освоить уже подключённую токенную аутентификацию DRF.

## 3. Архитектурные требования

1. Все API-маршруты имеют префикс `/api/v1/`.
2. HTML-маршруты и API-маршруты остаются раздельными. URL-файл сайта не должен одновременно служить URL-файлом API.
3. API-код располагается рядом с предметной областью. Для каталога допускается текущая схема с отдельными `urls_api.py` и сериализаторами; при росте API их можно собрать в пакет `catalog/api/`.
4. Не создавать отдельное верхнеуровневое Django-приложение `api` только ради маршрутизации существующих приложений.
5. Для каждого endpoint явно определить разрешённые HTTP-методы, аутентификацию и permissions.
6. Клиент не должен назначать владельца ресурса, автора, цену, остаток, статус заказа или признак оплаты, если эти значения должны определяться сервером.
7. Ошибки возвращаются в формате API. В ответах не раскрывать traceback, SQL и внутренние пути проекта.

## 4. Этап 1: публичный API каталога

### 4.1. Список товаров

Создать endpoint:

- `GET /api/v1/products/`

Endpoint доступен анонимным клиентам и работает только на чтение.

В ответе для каждого товара предусмотреть:

- `id`;
- `name`;
- `slug`;
- `category` с идентификатором, названием и slug категории;
- `brand`;
- `description`;
- `price` и `old_price`;
- `is_available`;
- `in_stock` как булев признак наличия;
- URL основного изображения;
- список тегов в виде строк.

Точный остаток `stock` публично не возвращать: клиенту достаточно признака наличия. Поле `views` в публичный ответ не включать, если оно не требуется клиенту.

В выдачу включать только товары, у которых `is_available=True` и `stock > 0`, и товары активных категорий. Это правило относится к API; поведение HTML-каталога в рамках данного этапа не менять.

### 4.2. Деталь товара

Создать endpoint:

- `GET /api/v1/products/{slug}/`

Деталь возвращает те же публичные поля, что список, а также дополнительные изображения товара с `alt_text` и признаком основного изображения.

Просмотр через API не должен увеличивать счётчик просмотров товара. Несуществующий или невидимый товар должен возвращать корректный ответ API об отсутствии ресурса.

### 4.3. Поиск и фильтрация списка

Поддержать query-параметры:

- `category` — slug категории;
- `brand` — точное значение бренда;
- `search` — поиск без учёта регистра в названии и описании;
- `min_price` — минимальная цена включительно;
- `max_price` — максимальная цена включительно.

Фильтры должны комбинироваться. Например, запрос по категории, бренду и диапазону цены одновременно должен вернуть пересечение условий.

Проверки входных значений:

- цена должна быть числом, допустимым для Decimal;
- отрицательные цены запрещены;
- `min_price` не может превышать `max_price`;
- несуществующая категория и некорректные параметры обрабатываются предсказуемо и не вызывают HTTP 500;
- определить и покрыть тестом поведение для неизвестных query-параметров.

Параметры фильтров валидировать отдельно от модели товара. Ошибки должны указывать, какое значение неверно.

### 4.4. Сортировка

Поддержать параметр `ordering` только со следующими значениями:

- `price` — цена по возрастанию;
- `-price` — цена по убыванию;
- `-views` — популярность;
- `-created_at` — новизна;
- `name` — название.

Произвольное значение параметра нельзя напрямую передавать в `order_by()`. При неизвестном варианте возвращать ошибку валидации с допустимыми значениями. Сортировка должна быть стабильной: при совпадающем основном значении использовать дополнительное поле, например `id`.

### 4.5. Пагинация

Использовать настроенную пагинацию `LimitOffsetPagination`.

Поддержать параметры:

- `limit` — максимальное число объектов в ответе;
- `offset` — число пропускаемых объектов.

Ограничить максимальный `limit`, чтобы запрос не мог вернуть весь каталог одним ответом. Ответ списка должен содержать общее количество объектов, ссылки на следующую и предыдущую страницы, а также `results`.

Важно: настройка пагинации в `settings.py` сама по себе не пагинирует queryset в обычном `APIView`. Представление списка должно использовать механизм DRF, который применяет пагинацию автоматически, либо явно запускать пагинатор.

### 4.6. HTTP-методы и доступ

Для списка и детали на этом этапе разрешён только `GET` (также стандартные безопасные методы `HEAD` и `OPTIONS`, если они поддерживаются DRF). Создание, изменение и удаление товаров через API не входят в этап 1.

### 4.7. Критерии приёмки этапа 1

- Анонимный клиент получает список и деталь товара в JSON.
- Все товары в ответе соответствуют установленной политике видимости.
- Теги представлены списком строк, изображения — URL, связанные модели — сериализованными значениями; в JSON нет объектов Manager.
- Фильтры можно комбинировать.
- Неверные цены, диапазоны и параметры сортировки обрабатываются без HTTP 500.
- Сортировка принимает только whitelist значений.
- Пагинация работает с `limit` и `offset`, размер страницы ограничен.
- Несуществующий товар возвращает корректный 404 API.
- Запрос детали через API не меняет `views`.
- HTML-каталог и его URL продолжают работать.

## 5. Этап 2: API-тесты каталога

Добавить тесты для списка и детали товаров. Тесты не должны зависеть от содержимого локальной базы или реальных файлов в `media`.

Проверить:

- успешный список и корректную структуру JSON;
- сериализацию категории, изображений и тегов;
- скрытие недоступного товара и товара из неактивной категории;
- поиск и каждый фильтр отдельно;
- совместное применение нескольких фильтров;
- неверный формат цены, отрицательное значение и перепутанные границы цены;
- все разрешённые сортировки и отказ на неизвестную;
- пагинацию, включая верхний лимит `limit`;
- ответ для неизвестного slug;
- отсутствие изменения счётчика просмотров;
- доступность существующих HTML-маршрутов после подключения API.

Этап 1 считается завершённым только после прохождения API-тестов и проверки HTML-каталога.

## 6. Этап 3: токенная аутентификация и профиль

Добавить endpoint получения DRF-токена для существующего пользователя и защищённый endpoint текущего пользователя:

- получение токена — использовать штатный endpoint DRF Token Authentication;
- профиль текущего пользователя — `GET /api/v1/users/me/`.

Для `me` требовать аутентификацию токеном. Возвращать только безопасные профильные поля, например идентификатор, имя пользователя, email и допустимые контактные данные профиля. Не возвращать пароль и служебные секреты.

Проверить:

- без токена endpoint профиля запрещён;
- правильный токен возвращает данные пользователя, которому он принадлежит;
- неверный токен не даёт доступ;
- невозможно запросить профиль другого пользователя подстановкой его ID;
- API-аутентификация не меняет работу Django login и сессий HTML-сайта.

Глобальный `AllowAny` не считать защитой. На защищённых API views permissions задавать явно.

## 7. Этап 4: отзывы

Добавить API отзывов, используя `ModelViewSet` и router для практики CRUD и `self.action`.

Предусмотреть:

- публичное чтение только активных отзывов;
- фильтрацию отзывов по товару;
- создание отзыва только аутентифицированным пользователем;
- назначение автора из `request.user`;
- изменение и удаление только владельцем отзыва;
- сохранение ограничения: один отзыв пользователя на один товар;
- проверку рейтинга в допустимом диапазоне.

Критерии приёмки:

- гость не может создать отзыв;
- автор не может быть подменён входными данными;
- нельзя изменить или удалить чужой отзыв;
- повторный отзыв отклоняется понятной ошибкой;
- неактивный отзыв не появляется в публичном списке.

## 8. Этап 5: избранное

Добавить защищённый API для избранных товаров текущего пользователя:

- получить своё избранное;
- добавить товар;
- удалить товар.

Владелец записи назначается сервером по `request.user`. Повторное добавление должно быть идемпотентным или возвращать заранее выбранный и протестированный результат; дубликаты в базе недопустимы.

Критерии приёмки:

- анонимный пользователь не читает и не меняет избранное;
- пользователь видит только собственные записи;
- нельзя добавить запись от имени другого пользователя;
- нельзя удалить чужую запись;
- несуществующий товар обрабатывается корректно.

## 9. Этап 6: корзина и заказы

Начинать только после фиксации бизнес-правил и тестов. Не переносить текущий HTML-процесс автоматически: сначала определить совместимость API-корзины с корзиной в Django session.

До разработки согласовать:

- допускается ли гостевой заказ через API;
- использует ли API ту же сессионную корзину или отдельную корзину пользователя;
- считается ли цена заново из базы при оформлении;
- что делать, если цена или остаток изменились после добавления товара;
- как проверять купон и сохранять размер скидки;
- как гость безопасно получает доступ к заказу;
- отправляется ли email при создании API-заказа.

Для оформления заказа:

- проверять товары, количество, доступность и остаток на сервере;
- не принимать от клиента итоговую цену, владельца, статус и `is_paid`;
- записывать заказ, позиции, цены и списание остатков согласованно в транзакции;
- исключить отрицательный остаток при одновременных заказах;
- сохранять цену товара на момент заказа в `OrderItem`;
- запретить просмотр чужих заказов;
- не считать заказ оплаченным без подтверждённой интеграции оплаты.

Критерии приёмки должны включать пустую корзину, неверное количество, недостаточный остаток, изменение цены, применённый и неприменимый купон, ошибку в середине оформления, конкурентную покупку и попытку прочитать чужой заказ.

## 10. Общие требования к тестированию

Для каждого endpoint проверить:

- разрешённые и запрещённые HTTP-методы;
- успешный сценарий;
- невалидные и граничные значения;
- ожидаемое поведение анонимного и авторизованного пользователя;
- запрет доступа к чужим объектам;
- невозможность подменить серверные поля;
- корректный формат данных и HTTP-статусов.

При изменении API запускать сначала тесты соответствующего приложения, затем полный набор тестов проекта. Ручная проверка в браузере полезна, но не заменяет автоматические тесты.

## 11. Порядок выполнения

1. Завершить API списка и детали каталога.
2. Добавить фильтрацию, сортировку и пагинацию.
3. Написать тесты каталога и проверить HTML-сайт.
4. Добавить token endpoint и `/users/me/`.
5. Реализовать отзывы с проверкой владельца.
6. Реализовать избранное текущего пользователя.
7. Спроектировать и протестировать правила корзины и заказов.
8. Только после этого добавлять API оформления заказов.

Первый этап ограничен чтением каталога. Не добавлять в него регистрацию, изменение товаров, отзывы, корзину или заказы.
